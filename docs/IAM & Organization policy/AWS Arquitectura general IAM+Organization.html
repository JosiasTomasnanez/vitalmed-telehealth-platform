📘 Criterios de Diseño, Racional de Gobernanza y Decisiones de Arquitectura

Fundamentos técnicos y operacionales que justifican la topología multi-cuenta, gestión de identidades y controles de seguridad para VitalMed.

🏥 Contexto del Negocio y Regulaciones de Salud

VitalMed opera en múltiples jurisdicciones de Latinoamérica (Argentina, Chile, Colombia, México), procesando Datos Personales Sensibles y Historias Clínicas Electrónicas. Debido a las regulaciones de protección de datos de salud de cada país (p. ej., Ley 25.326 AR, Ley 1581 CO, equivalentes HIPAA / GDPR), era indispensable garantizar un aislamiento estricto de datos y blast radius reducido sin multiplicar la complejidad operativa del equipo técnico.

ADR-001 Aprobado

Estructura Multi-Cuenta por País vs. Multi-Tenant Monolítico

Criterio evaluado: Reducción de radio de impacto (Blast Radius) y cumplimiento de residencia local de datos de clínicas.

Decisión: Separar cada país en una cuenta AWS independiente bajo la OU Workloads, restringiendo la conectividad cruzada entre ellas.

✓ Beneficio: Un compromiso o fallo en una cuenta (credenciales filtradas, error de despliegue) jamás compromete las bases de datos ni servicios de los demás países, aunque compartan la misma región física.

ADR-002 Aprobado

IAM Identity Center (SSO) & Cero Claves Estáticas

Criterio evaluado: Prevención de fugas de credenciales en repositorios y trazabilidad unificada de auditoría.

Decisión: Prohibir la creación de usuarios IAM locales con llaves de acceso estáticas (Access Key ID / Secret Key) mediante SCP a nivel Root.

✓ Beneficio: Autenticación federada SSO con MFA obligatorio y credenciales temporales rotativas con validez limitada (max 1 a 8h).

ADR-003 Aprobado

Autenticación de CI/CD mediante OIDC Trust (GitHub Actions)

Criterio evaluado: Eliminación de secretos de AWS guardados en el proveedor de CI/CD externo.

Decisión: Configurar OpenID Connect (OIDC) para que GitHub Actions solicite tokens de corta duración firmados criptográficamente.

✓ Beneficio: Si un repositorio es vulnerado, no hay secretos expuestos para extraer ni reutilizar fuera de los despliegues autorizados.

ADR-004 Aprobado

Despliegue de Aplicaciones con ECS Task Roles Independientes

Criterio evaluado: Separación entre el runtime de infraestructura del contenedor y el código de negocio.

Decisión: Utilizar ExecutionRole solo para tirar de la imagen Docker y enviar logs, y TaskRole exclusivo para consultas a la DB y Secrets.

✓ Beneficio: El código del microservicio sólo tiene los permisos strictly indispensables durante su tiempo de ejecución.

ADR-005 Supuesto explícito

Mono-Región (us-east-1) vs. Multirregión por País

Criterio evaluado: AWS no tiene región propia en Argentina, Chile ni Colombia (la más cercana es sa-east-1, São Paulo); México sí cuenta con región propia desde 2025 (mx-central-1). Desplegar en múltiples regiones agrega latencia inter-región, replicación de KMS multi-región y costos de transferencia de datos que un equipo de 12 personas no puede sostener de forma sostenible.

Decisión (supuesto): Se desestima la multirregión y se opta por una sola región (us-east-1), resolviendo la separación regulatoria exigida por el caso exclusivamente vía aislamiento lógico por cuenta (Organizations + SCP + KMS por cuenta), no vía aislamiento geográfico.

✓ Beneficio: menor costo y complejidad operativa. ⚠️ Trade-off a documentar en la defensa: un incidente regional de AWS en us-east-1 afectaría a los 4 países simultáneamente (a diferencia de un esquema multirregión); se acepta ese riesgo a cambio de simplicidad operativa, dado el tamaño del equipo.

🔄 Flujo Operativo de Seguridad y Ciclo de Vida del Acceso

Paso 1: Identificación

El usuario o servicio solicita acceso a través del portal de AWS Identity Center o token OIDC temporal.

Paso 2: Evaluación SCP

AWS verifica las Service Control Policies root (p. ej. región válida, acciones prohibidas como borrar audit logs).

Paso 3: Asunción PoLP

Se otorga únicamente el Permission Set o IAM Role correspondiente al perfil (DevOps, Dev, Security Auditor).

Paso 4: Auditoría WORM

Toda llamada a API se centraliza de manera inmutable en CloudTrail dentro de la cuenta Log Archive.
